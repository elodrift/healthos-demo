# Gate B review — PR #19, read-API ticket and engine vocabulary

verdict: PASS

**Reviewer:** Cowork advisor session, 23 Aug 2026. Did not author either file —
the ticket and the `CONTEXT.md` edit were written by the 20 Aug grill session.
This review was written after reading both files in full, not from the commit
message or the kit's summary of them.

**Scope:** 2 files, +299/−3, documentation only. No code path, no route, no
schema, no dependency. Gate B fires here on diff size alone (CLAUDE.md §7,
~50-line threshold, no docs exemption) — correctly, in this reviewer's view:
`CONTEXT.md` is the file every future agent reads to learn what "lane",
"confidence" and "portionBasis" mean, so its per-line consequence is higher
than most code's, not lower.

## What was checked

- Internal consistency of the status union against the acceptance criteria.
- Whether the vocabulary added to `CONTEXT.md` collides with, or silently
  redefines, terms already in that file.
- Whether any binding claim contradicts ADR-023, Decision 10, or standing
  rule #5.
- Whether the "out of scope" list actually excludes what the body assumes.

## Findings — no P1, no P2. Four P3 notes, none blocking.

1. **`computedAt` is on `STALE` in the illustrative union but not on `OK`.**
   Acceptance criterion 7 requires it on "any response that could be shown as
   stale", and an `OK` response left open in a tab becomes exactly that.
   `CONTEXT.md` §6 also has the client building its freshness wrapper from a
   raw `computedAt`, which it would not have on `OK`. The union is explicitly
   labelled non-binding and the criterion governs, so this is a note for the
   engine side, not a defect in the contract: ship `computedAt` on every
   plan-bearing variant, not just `STALE`.

2. **`DEGRADED` is absent from the required fixture coverage**, and it is the
   one variant carrying a free-text field (`reason: string`). The document's
   own thesis is that every case is named and nothing is inferred; free text is
   where that principle bends, so it is the variant most worth pinning in a
   fixture. `Absent = { reason: string }` has the same shape. Worth the engine
   side considering an enum plus optional detail rather than a bare string —
   but this is explicitly the engine's call and the ticket says so.

3. **Line 74 punctuation:** "(a) every case is named, none inferred from a
   missing field**:** (b) …" — the colon should be a semicolon. Cosmetic.

4. **`schemaVersion` appears in the acceptance criteria but not in the
   illustrative union shape.** Harmless, since the shape is marked
   non-binding, but a reader skimming only the code block would miss a
   required field.

## What this review did not check

Whether the contract is *buildable as specified* on the engine side. That is
the engine repo's judgment, and the ticket correctly leaves implementation,
variant naming, and the planner-provenance vocabulary to it. The open item at
lines 152–159 is properly marked as engine-owned and unresolved; it is not a
gap in this document.

## Why PASS

Every binding requirement is internally consistent, cites its authority
(ADR-023, Decision 10, standing rule #5), and states its own scope limits.
The four notes above are refinements to a document that explicitly defers
implementation, not defects in what it binds.
